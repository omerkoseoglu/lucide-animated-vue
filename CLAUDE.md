# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this project is

Vue 3 / Nuxt port of [`pqoqubbw/icons`](https://github.com/pqoqubbw/icons), a React library of 439 animated icons (Lucide SVGs + hover/imperative animations). Goal: reimplement every icon 1:1 in Vue, preserving each icon's specific animation behavior (timing, easing, variants), using Nuxt + `motion-v` instead of Next.js + `motion/react`.

## Status

436/439 icons ported and verified working in the browser (all auto-generated by the codemod below). Not yet ported (needs a hand port — see "Known gaps"): `keyboard`, `volume`, `wifi-low`.

Deployed at https://omerkoseoglu.github.io/lucide-animated-vue/ (GitHub Pages, auto-deployed on push to `main` — see "Deployment" below).

## Deployment

The whole site is prerenderable — every route is known at build time (the icon list, all 436+ detail pages), nothing needs a live server — so it ships as a **static** build via Nitro's `github-pages` preset, not the Node server build.

- `.github/workflows/deploy.yml` runs on every push to `main`: `pnpm generate` with `NITRO_PRESET=github-pages` and `NUXT_APP_BASE_URL=/lucide-animated-vue/`, then `actions/upload-pages-artifact` + `actions/deploy-pages`. Pages itself is configured (via `gh api repos/omerkoseoglu/lucide-animated-vue/pages`) with `build_type: workflow`, so GitHub serves whatever the workflow uploads — no `gh-pages` branch involved.
- **Why `app/composables/useSiteOrigin.ts` exists**: the install command (shown in `CliInstallBlock.vue` and the icon detail page) needs the site's real origin + base path. A GitHub Pages / static deploy serves the exact same prerendered HTML to every visitor regardless of domain, so baking in a build-time or SSR-request origin (`useRequestURL()`) would be wrong or stale. `useSiteOrigin()` instead reads `window.location.origin` client-side on mount (correct for wherever the static output ends up being served — GitHub Pages, a fork's Pages, a custom domain, ...) and combines it with `useRuntimeConfig().app.baseURL` (set via `NUXT_APP_BASE_URL` at generate time) to build the full `<origin><base>r/<name>.json` URL. Don't swap this back to `useRequestURL()` — it broke exactly this way before the fix (worked fine on `pnpm dev`, silently wrong on the static deploy).
- If you ever need the Node server build (`pnpm build` + `pnpm preview`, or deploying somewhere that runs a real Nitro server) instead of the static one, `useSiteOrigin()` still works — `window.location.origin` is correct there too, just resolved one tick later (after client mount) instead of from the SSR request.
- Local dev (`pnpm dev`) is unaffected: no `NUXT_APP_BASE_URL` is set locally, so `base` resolves to `/`.

## Demo site

`app/pages/index.vue` (searchable icon grid) and `app/pages/icons/[name].vue` (per-icon detail page: replay button, usage snippet, source view, both copyable) are a small demo app, loosely mirroring upstream's Next.js site. They're driven by `app/composables/useIconRegistry.ts`, which:

- discovers every `app/components/icons/*.vue` file via `import.meta.glob` (both the compiled component and, separately, its raw source text via `{ query: '?raw', import: 'default' }`)
- derives the kebab-case display name from the PascalCase filename (`toKebab()` — handles digit runs like `ArrowDown01Icon` → `arrow-down-0-1` and single-letter-prefixed names like `AArrowDownIcon` → `a-arrow-down`)
- attaches search keywords from `app/utils/icon-keywords.json`, generated by `scripts/extract-keywords.mjs` from upstream's `ICON_LIST` in `.reference-icons/icons/index.ts` (re-run it after porting new icons upstream has keywords for)

If you add a new page that needs the icon list, use `useIconRegistry()` rather than re-deriving it — the glob + keyword-join logic isn't trivial to get right twice (see the digit/prefix edge cases above).

The demo site's UI is built with [shadcn-vue](https://www.shadcn-vue.com/) (`Button`, `Input`, `Badge`, `Card` in `app/components/ui/`) + Tailwind v4, not hand-rolled CSS. Add more shadcn-vue components with `pnpm dlx shadcn-vue@latest add <name>` rather than writing raw component markup by hand — but see the pnpm gotcha below first.

### shadcn-vue registry (installable icons)

Every icon is published as its own [shadcn-vue registry item](https://www.shadcn-vue.com/docs/registry) at `public/r/<name>.json`, so anyone can `npx shadcn-vue@latest add <site-url>/r/<name>.json` to drop a single icon into their own project (installs the `.vue` file to `components/icons/` via the item's `target` path, and adds `motion-v` to their `package.json` — verified end-to-end against the real CLI in a scratch project, not just schema-shape-checked).

- `scripts/build-registry.mjs` generates all of this: one `public/r/<name>.json` per icon (full file content, `type: "registry:component"`, `dependencies: ["motion-v"]`), plus `public/r/registry.json` and root `registry.json` (a catalog listing every item *without* file content, per the shadcn registry.json spec — content only lives in the per-item files that get fetched at install time).
- Re-run `node scripts/build-registry.mjs` after porting new icons or changing an existing icon's source.
- The detail page (`app/pages/icons/[name].vue`) and `CliInstallBlock.vue` build the install command from `useSiteOrigin()` (see "Deployment" above) — always correct for wherever the site is actually being served, no hardcoded URL to keep in sync.
- Upstream's own registry (`.reference-icons/scripts/registry-build.ts`) was the reference for this — same two-tier shape (full-content item files + content-stripped root catalog), adapted from their React/shadcn (`registry:ui`) version to ours (Vue/shadcn-vue, `registry:component`).

### pnpm build-approval gotcha (`ERR_PNPM_IGNORED_BUILDS`)

pnpm 10+ has two *separate* mechanisms here, and only having one of them in `pnpm-workspace.yaml` is a silent trap: `onlyBuiltDependencies` just lists which packages are *eligible* to run install scripts — it does **not** itself approve them. Without a matching `allowBuilds` map recording the actual yes/no, a from-scratch `pnpm install --frozen-lockfile` (any fresh clone, any CI runner) fails with `ERR_PNPM_IGNORED_BUILDS` and **exit code 1** — this bit us in GitHub Actions even though `onlyBuiltDependencies` was already committed and correct, because `allowBuilds` was missing. (If you test this locally and it seems to pass, check you didn't pipe the command through something like `| tail` — that silently swaps the exit code you see for the pipe's, masking exactly this failure.)

The fix, once, from a clean `node_modules`:
```bash
rm -rf node_modules && pnpm install --frozen-lockfile   # fails, that's expected — creates node_modules first
pnpm approve-builds --all                                # non-interactive; runs the pending scripts AND writes allowBuilds
pnpm install --frozen-lockfile                            # now clean, exit 0
```
Commit the resulting `pnpm-workspace.yaml` (should have both `allowBuilds` and `onlyBuiltDependencies`). Separately: the `shadcn-vue` CLI shells out to `pnpm add` internally, and if it hits an unapproved build in a non-interactive shell it **overwrites `pnpm-workspace.yaml`** with a broken placeholder (`allowBuilds:\n  vue-demi: set this to true or false`) instead of real values, then fails. If a `shadcn-vue add`/`init` command fails this way: restore `pnpm-workspace.yaml` from git (`git checkout -- pnpm-workspace.yaml`), then re-run the three commands above for whatever new package it choked on, then retry the `shadcn-vue` command.

## Reference clone

`.reference-icons/` is a shallow clone of the upstream repo, gitignored, **read-only source of truth for porting**. Do not edit it, do not commit it. Re-clone or `git -C .reference-icons pull` if it's stale relative to upstream.

- Source icon files: `.reference-icons/icons/<kebab-name>.tsx`
- Icon list/registry: `.reference-icons/icons/index.ts`
- Upstream contribution guide (animation quality bar, naming rules): `.reference-icons/CONTRIBUTING.md`

## Tech stack

- Nuxt 4 (`app/` directory structure, i.e. Nuxt 4's new default layout)
- Vue 3 `<script setup lang="ts">`
- `motion-v` (`motiondivision/motion-vue`) — the official Vue port of Motion (ex-Framer Motion). It shares the same underlying engine as `motion/react`, so animation timing/easing/springs port faithfully, not just approximately. Registered via the `motion-v/nuxt` module in `nuxt.config.ts`.
  - **Every icon component must still `import { motion, useAnimationControls } from 'motion-v'` itself.** The Nuxt module does not make the `<motion.svg>` dot-tag syntax resolve on its own — Vue's SFC compiler only compiles `<motion.svg>` into a member-expression component lookup when `motion` is a binding local to that file's `<script setup>`. Skipping the import makes Vue treat `motion.svg` as a literal (nonexistent) global component name — it fails silently with a console warning, not a build error, so this is easy to miss.
  - `useAnimationControls()` is a near-exact match for React's `useAnimation()`: `controls.start(nameOrObject)` returns a `Promise` that resolves when the animation finishes, so `await controls.start(...)` sequences port verbatim.
- `nuxt.config.ts` registers `app/components/icons` with `pathPrefix: false` — without it, Nuxt's directory-based auto-import would register `HeartIcon.vue` as `<IconsHeartIcon>` instead of `<HeartIcon>`, breaking every reference to these components.
- Tailwind CSS v4 (via `@tailwindcss/vite`) + `shadcn-nuxt` module + `shadcn-vue` CLI for the demo site's UI components (`app/components/ui/`, `components.json`, `app/lib/utils.ts`'s `cn()` helper).
- pnpm — `pnpm-workspace.yaml` sets `onlyBuiltDependencies: [esbuild, vue-demi]` so `pnpm install` doesn't stall on the build-script approval prompt in non-interactive shells (see the shadcn-vue CLI gotcha below — it likes to break this file).

## Icon component pattern

Each source file in `.reference-icons/icons/*.tsx` follows one fixed React pattern (documented in their `CONTRIBUTING.md`): a `forwardRef` component exposing `{ startAnimation, stopAnimation }` via `useImperativeHandle`, hover-triggered by default, driven by Motion `variants`. Port every icon to the equivalent Vue idiom:

| React (`motion/react`) | Vue (`motion-v`) |
|---|---|
| `forwardRef` + `useImperativeHandle` | `defineExpose({ startAnimation, stopAnimation })` |
| `useAnimation()` controls object | `useAnimationControls()` — same object, same `.start()`/`.stop()` API, bound via `:animate="controls"` |
| `isControlledRef` (any name/shape upstream uses — `useRef(false)`, `!!ref`, `ref != null`, ...) | our own `const isControlled = ref(false)`, set `true` inside `startAnimation`/`stopAnimation` |
| `<motion.svg animate={controls} variants={...}>` | `<motion.svg :animate="controls" :variants="...">` |
| `custom={n}` prop for per-child variants | `:custom="n"` — identical API |
| helper `useCallback` functions (e.g. `resetToNormal`, `triggerEffect`) | plain `function` declarations, called the same way |
| `size` prop, default `28` (occasionally a different default — check the source) | same |

Canonical shape for `app/components/icons/<PascalName>Icon.vue`:

```vue
<script setup lang="ts">
import type { Variants } from 'motion-v'
import { motion, useAnimationControls } from 'motion-v'
import { ref } from 'vue'

interface Props {
  size?: number
}

withDefaults(defineProps<Props>(), { size: 28 })

const variants: Variants = {
  normal: { /* ... */ },
  animate: { /* ... */ }
}

const controls = useAnimationControls()
const isControlled = ref(false)

function startAnimation() {
  isControlled.value = true
  controls.start('animate')
}

function stopAnimation() {
  isControlled.value = true
  controls.start('normal')
}

defineExpose({ startAnimation, stopAnimation })

function handleMouseEnter() {
  if (!isControlled.value) controls.start('animate')
}

function handleMouseLeave() {
  if (!isControlled.value) controls.start('normal')
}
</script>

<template>
  <div @mouseenter="handleMouseEnter" @mouseleave="handleMouseLeave">
    <motion.svg
      :animate="controls"
      :variants="variants"
      fill="none"
      :width="size"
      :height="size"
      viewBox="0 0 24 24"
      stroke="currentColor"
      stroke-width="2"
      stroke-linecap="round"
      stroke-linejoin="round"
    >
      <!-- paths/lines copied from the matching .reference-icons/icons/*.tsx -->
    </motion.svg>
  </div>
</template>
```

Reference implementation: `app/components/icons/HeartIcon.vue`. For icons with independently-animated children sharing one variants object (e.g. `menu.tsx`'s three `<motion.line>`s + `custom`), keep that shared-variants-plus-index structure rather than flattening it. Icons with no hover behavior at all (only imperative start/stop — e.g. `concierge-bell.tsx`) get no `@mouseenter`/`@mouseleave` on the root `<div>`; don't invent hover behavior upstream doesn't have.

### SVG attribute casing

Vue's SFC template compiler does **not** case-normalize attribute names the way HTML parsing does — whatever case you write is what gets set on the DOM element. Get this wrong and the icon silently renders wrong (e.g. no viewBox → no visible icon at certain sizes):

- Camel in the SVG spec itself, keep camel: `viewBox`, `pathLength`, `patternUnits`
- Everything else React writes as camelCase has a real kebab-case SVG attribute — convert it: `strokeWidth`→`stroke-width`, `strokeLinecap`→`stroke-linecap`, `strokeLinejoin`→`stroke-linejoin`, `strokeDasharray`→`stroke-dasharray`, `strokeOpacity`→`stroke-opacity`, `fontSize`→`font-size`, `fontWeight`→`font-weight`, `textAnchor`→`text-anchor`, `dominantBaseline`→`dominant-baseline`
- `className` → `class`

### Naming

- Source: `icons/<kebab-case-name>.tsx`, e.g. `icons/arrow-big-up-dash.tsx`
- Port: `app/components/icons/<PascalCase><Suffix>Icon.vue`, matching the exported name in the source file (check `icons/index.ts` for the canonical name — it occasionally diverges from the filename).

### What NOT to carry over

- No `"use client"` directive, no `cn()` className merge helper, no `HTMLAttributes<HTMLDivElement>` prop spreading, no manual `onMouseEnter`/`onMouseLeave` prop passthrough — Vue's attrs fallthrough already merges a parent's own `@mouseenter`/`@mouseleave` listeners onto the root element for free, so the explicit passthrough React needs is dead weight here.
- Don't add `strokeDasharray`/`strokeDashoffset` "draw-in" animations for new/custom icons — upstream explicitly rejects these as low-quality (see `CONTRIBUTING.md`); only port them if the *original* icon itself already uses that technique.

## Porting tooling

`scripts/port-icons.mjs` is a codemod (Babel AST-based) that mechanically translates `.reference-icons/icons/*.tsx` into the Vue pattern above. It handles the vast majority of icons, including multi-`useAnimation()` icons (independent controls per part), `.map()`-rendered repeated elements (→ `v-for`), async/sequenced `controls.start()` chains, and arbitrarily-named helper functions/consts declared inside the component body.

```bash
node scripts/port-icons.mjs             # port every not-yet-generated icon (skips existing output files)
node scripts/port-icons.mjs --force     # regenerate everything, overwriting hand edits
node scripts/port-icons.mjs --dry       # report what would happen, write nothing
node scripts/port-icons.mjs --only=heart,menu   # limit to specific icons (kebab-case source names)
```

After running it, always:
1. `npx prettier --write "app/components/icons/*.vue" --print-width 100` — the codemod emits unformatted single-line output.
2. `node scripts/validate-icons.mjs` — compiles every generated SFC's script/template via `@vue/compiler-sfc` to catch malformed output (does not catch everything — see "Known gaps in the codemod" below).

It intentionally throws (skips the file, reports it) rather than guessing on anything it doesn't recognize: `useState`/`useEffect`/`useMemo`/other unhandled hooks, `AnimatePresence`-driven conditional logic beyond a plain `.map()`, destructured `const [a, b] = ...`. Those need a hand port.

### Known gaps

- `keyboard.tsx`, `volume.tsx`, `wifi-low.tsx` use `useState`/`useEffect` for timed/toggled animation sequences the codemod doesn't attempt to translate — port these by hand.
- The codemod's own validation (`validate-icons.mjs`) only catches script/template compile errors. It has previously missed: (a) an unescaped inline array literal breaking a generated `v-for` attribute when the array spanned multiple lines, (b) the missing `motion` import described above, (c) Nuxt's default component-name prefixing. All three are fixed in the current script, but if you extend the codemod, re-verify by actually rendering a page that references the changed icons in a browser (dev server + hover test), not just by running the two validation commands — those alone did not catch (b) or (c).
